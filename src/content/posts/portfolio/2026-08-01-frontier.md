## Tech Stack
* **Backend:** Java, Spring Boot
* **Auth:** JWT ES256/RS256, Steam Web API
* **Database:** MySQL
* **Reliability:** Optimistic Lock, Idempotency-Key, Transactional Outbox
* **Admin:** 운영 대시보드 API

## 주요 구현 기능

### 1. Steam 티켓 인증
**"외부 플랫폼 인증 결과를 서버 세션으로 안전하게 변환"**
* 클라이언트가 전달한 Steam 티켓을 Steam Web API로 검증했습니다.
* 검증된 Steam 계정만 내부 사용자로 매핑하고 Access/Refresh Token을 발급했습니다.
* Refresh Token 회전과 재사용 감지를 적용해 탈취 토큰 재사용 위험을 줄였습니다.

### 2. 레이드 결과 서버 판정
**"게임 결과를 클라이언트가 아닌 서버에서 최종 확정"**
* 로비 인벤토리, 레이드 인벤토리, 장비 인벤토리를 컨테이너 모델로 추상화했습니다.
* 탈출 성공 시 `RaidInventory`의 아이템을 `LobbyInventory`로 확정 반영했습니다.
* 사망 시 전리품과 출정 장비 손실 정책을 서버 트랜잭션 안에서 처리했습니다.

### 3. 동시성 및 멱등성 처리
**"중복 요청과 경합 상황에서도 아이템 원장을 보호"**
* 인벤토리 변경 요청에 version/revision 기반 낙관적 잠금을 적용했습니다.
* `Idempotency-Key`를 사용해 네트워크 재시도나 중복 클릭으로 같은 보상이 반복 지급되지 않게 했습니다.
* 아이템 이동과 레이드 정산은 하나의 트랜잭션 경계 안에서 처리했습니다.

### 4. 운영 대시보드
* 유저, 아이템, 레이드 지표를 조회할 수 있는 관리자 API를 구현했습니다.
* `ItemInstance` 원장을 기준으로 아이템 이동과 정산 결과를 추적할 수 있게 구성했습니다.
* 운영자가 비정상 지급, 레이드 실패, 사용자 상태를 빠르게 확인할 수 있도록 조회 기준을 분리했습니다.

## 구현 방식
* **서버 권한 구조:** 루팅, 사망, 탈출, DB 저장 결과를 서버가 결정하도록 설계해 클라이언트 조작 가능성을 줄였습니다.
* **컨테이너 도메인 모델:** Lobby, Raid, Equipment 인벤토리를 같은 컨테이너 추상화로 다루어 아이템 이동 로직의 중복을 줄였습니다.
* **원자적 정산:** 레이드 결과 반영과 이벤트 기록을 트랜잭션으로 묶어 중간 실패 시 데이터가 어긋나지 않게 했습니다.
* **이벤트 발행 안정화:** DB 커밋 이후 필요한 후속 처리를 위해 Transactional Outbox 패턴을 적용했습니다.

---

## 트러블 슈팅 및 최적화
* **인벤토리 중복 지급/복제:** 동일 요청이 반복되거나 경합이 발생할 때 아이템이 중복 반영될 수 있어 낙관적 잠금과 `Idempotency-Key`를 함께 적용했습니다.
* **레이드 정산 중 예외 시 데이터 유실:** DB 반영과 이벤트 발행 시점이 분리되면 정산 결과가 누락될 수 있어 Transactional Outbox로 커밋과 이벤트 기록의 원자성을 확보했습니다.
* **클라이언트 결과 조작 위험:** 탈출, 사망, 보상 확정 값을 클라이언트 전달값에 의존하지 않고 서버 판정 결과만 저장하도록 변경했습니다.
* **운영 조회 부담:** 유저, 아이템, 레이드 지표 조회 목적을 분리해 대시보드 API가 게임 플레이 트랜잭션에 영향을 주지 않도록 구성했습니다.

## 성과
* 게임 백엔드에서 중요한 인증, 세션, 인벤토리, 레이드 정산 흐름을 서버 권한 중심으로 설계했습니다.
* 낙관적 잠금, 멱등성 키, Transactional Outbox를 적용하며 분산 환경에서 데이터 정합성을 지키는 구현 경험을 확보했습니다.
